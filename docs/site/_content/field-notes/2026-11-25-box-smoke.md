# Boxes, phase 2 and the Linux half of phase 10: the supervisor, both tiers, and a smoke test

**Date:** 2026-11-25
**Status:** on the branch, dark (`SLAUDE_BOX=off`, `SLAUDE_BOX_TIER=none` are still the defaults). A real node worker has run sessions in real sandboxes, on both tiers, **on a development VM on a Mac and in a privileged container on that VM. Not on a cluster. No real model and no real provider credential was involved.**
**Plan:** `docs/superpowers/plans/2026-11-24-box-implementation.md`, Phases 2 and 10. **Spec:** `docs/superpowers/specs/2026-11-24-box-design.md`.

## Re-run it

```sh
scripts/smoke/box-smoke.sh            # both tiers, then both again nested in a privileged container
scripts/smoke/box-smoke.sh gvisor     # one tier
SLAUDE_SMOKE_NESTED=0 scripts/smoke/box-smoke.sh   # without the container stage
```

On macOS the script re-runs itself inside the Colima VM (`colima ssh`); it does not start or stop the VM. On Linux it needs root, Docker, runsc, skopeo and umoci, and at least 3 GB free under `/var/lib/slaude-smoke` (a node refuses to start a sandbox with under 1 GB free on its box volume, which is the admission rule doing its job). It needs no credential: the model is `e2e/mock-llm`, and "the provider's real credential" is a random string the test invents.

What it runs, per tier. Both files are skipped by a plain `bun test`:

- `tests/box/tier-contract.test.ts`: the sandbox contract, one file for both tiers, the supervisor in the test process.
- `tests/node/worker-box-real.test.ts`: a gateway and its `/v1` server, a node worker started with `SLAUDE_BOX_TIER=<tier>` and no driver of its own (so it runs boxes through the supervisor, as a deployment does), the supervisor as a separate root process with a clean environment, the real CLI inside a box, the mock model behind a guard that records the credential of every model request.

## What the first real sandbox found

None of these could be seen before a driver existed. All are fixed.

1. **The pinned digest never reached the node.** The gateway's session view carries `box_name` and `box_digest`; the node's session store dropped them, so every boxed session failed its boot as "not pinned to a digest". Phase 3's tests passed because they supplied the row directly.
2. **A new session's home was not mounted.** The mount list skipped sources that did not exist, and a first home does not exist until the supervisor creates it. The agent then wrote "home" into the image's own `/home/agent`, in the throwaway overlay. The durable-home assertion caught it.
3. **A fork loop took a gVisor sandbox down.** The cgroup `pids` limit counts the sandbox's own threads, and a sandbox that reaches it does not refuse a fork: its kernel process cannot start a thread and the whole sandbox stops. The box's limit is now `RLIMIT_NPROC` inside the sandbox, with the cgroup limit far above it as a backstop. That alone was not enough: `RLIMIT_NPROC` is counted per user, so box-init, running as the agent, could not start a thread either and died, which also ends the sandbox. box-init now runs as its own user (65534).
4. **The supervisor did not stop while a worker was connected**, and kept starting sandboxes after it was told to stop. It now refuses new work and ends its connections first.
5. **As pid 1 of a container the supervisor kept a zombie for every process a bwrap box ran.** bwrap leaves an ended process for pid 1 to reap, and a Bun process reaps only its own children. The zombies (seen in `/proc`, one `bwrap` each) stay charged to the sandbox's cgroup. runsc's detached sandbox processes are orphans of the same kind; that was not checked. The image now ships `tini` and the supervisor warns when it is pid 1: **the supervisor container's command must be `tini -- bun --no-env-file src/box/boxd/main.ts ...`** (phase 9's manifests have to say so). With `tini` as pid 1 the count returns to idle on both tiers.
6. **The supervisor's own environment reached runsc and bwrap.** Seen once and not isolated: in a run whose `TMPDIR` named a directory that no longer existed, every runsc sandbox exited before its container started, while bwrap boxes ran. Every program the supervisor starts now gets a search path and nothing else.
7. **Bun reports a refused or missing Unix socket before a listener attached after `connect()` can hear it**, and an unheard error event ends the process. In box-init that would have ended a box whenever a relay was dialed before the worker's socket existed. Sockets are now created, given their listeners, then connected, in box-init, the supervisor's client and the egress proxy.
8. **An `async` function that returns another async function's rejected promise** was reported by Bun as an unhandled rejection even though the caller awaited it. The supervisor's request switch awaits.
9. **The last output and the exit status of a process were lost** when the supervisor destroyed the stdio connection right after ending it.
10. **A boxed session's scratch directory was unreachable for the supervisor** (it lived in the node container's temp area) and failed the worker's ownership check once it was handed to the sandbox's user. On a node that runs boxes it now lives on the box volume, and the agent uid is an accepted owner.
11. **One turn in one full run failed on its first model request**, on the bwrap tier, with the CLI reporting an error result and no tool call. The cause was not established. The likeliest one is a connection the provider proxy (or the test's guard in front of the mock) had kept from an earlier request and the upstream had closed since: the first write on it fails before any answer. The provider proxy now reads a request's body whole and sends it once more, on a fresh connection, when the first attempt gets no answer at all; the test's guard opens a connection per request. Three full runs since have passed, which does not prove the cause.
12. **The mock model loops on a second multi-tool turn of a resumed thread.** The CLI, loading a transcript, drops a tool call whose id an earlier turn used; the mock numbers its calls from 1 every turn, never sees a result and asks again until the request is too large. The mock takes an optional `id=<word>`. This is the mock's, but the HA suite's cold-resume case would hit it the same way.

## Decisions taken while building it

**Two tiers behind one supervisor and one driver.** The gVisor and bwrap drivers are the same code with a different tier name; the supervisor has a backend per tier. Everything above (image cache, mounts, proxies, environment, packs, admission) is shared, so the choice between them stays a configuration value.

**bwrap is not gVisor with a different binary.** What differs, measured:

- There is no long-lived sandbox process. Each process the worker starts is its own `bwrap` (its own pid, network, ipc and uts namespace) on the session's overlay root, mounts and cgroup, with box-init in front of it for the relays. Nothing an agent leaves running outlives its CLI.
- Unprivileged user namespaces are refused on this host (Ubuntu 24.04, AppArmor): bwrap run as uid 10001 fails. So the supervisor runs bwrap as root with a user namespace in which root appears as the agent, with every capability dropped and further user namespaces disabled. **A box's files are root's on the node's disk on this tier**, and inside the box the agent "owns" the image's files, so it can write system directories (into the overlay; the image directory is never written).
- The root overlay is a kernel overlay on the node's disk. **It has no size limit of its own.**
- The kernel is shared. A seccomp deny list is loaded (mount and the new mount API, namespaces, modules, keyrings, bpf, perf, io_uring, the clock), written as a BPF program in TypeScript with a table test that runs the filter, and one live check: `keyctl`, which needs no privilege, answers EPERM in a box. It is a short deny list, not an allow list.
- At the process limit the cgroup refuses forks for everything in it, box-init included.

**Under gVisor the agent cannot write a system directory at all.** It is uid 10001 with no capability, and the image's files are root's. The spec's "a runtime `apt install` is not durable" is, on this tier, "not possible". Tools install into the home.

**Who owns a session's files.** The sandbox's user must own what it writes, and the node worker reads and writes the same workspace, config directory and scratch directory. The supervisor hands every read-write mount to the sandbox's host owner before a start (uid 10001 under gVisor, its own uid under bwrap). So the node worker must be root (either tier) or uid 10001 (gVisor). A worker under another uid is not supported.

**What a box is not given.** The slaude home is a plugin directory for the SDK and also holds every session's workspace: a box gets its plugin parts (`skills/` and the like), never the home. The base config home's `projects/` holds every session's transcript: a box gets the one folder of its own working directory, at its unchanged path, so the transcript unit is the same boxed and unboxed.

**Pack work runs in a child process of the supervisor.** Scanning and compressing a large home is seconds of synchronous work, and the supervisor's event loop carries every box's stdio.

**Abort.** `/abort` ends the CLI process; the worker then stops the session's sandbox with it. The supervisor ends a gVisor process with `runsc kill --pid` on the pid of its own pid namespace, and a bwrap process by ending the first process of its namespace (ending bwrap itself orphans it).

**A Unix socket path holds about 100 bytes.** `SLAUDE_BOX_DIR/sessions/<session id>/run/egress.sock` must fit; the driver refuses a box directory that is too long instead of failing to listen.

## Deviations from the plan

- `SLAUDE_BOX_DEV_IMAGE` was never added: phase 4 (the image cache and the pin in the session view) landed first.
- The image is unpacked by the node worker's image cache (phase 4), not by the supervisor. The supervisor only reads `images/<digest>/rootfs`. `image.import`, `image.list` and `image.remove` exist in the protocol and call the same cache.
- The image cache now keeps the image's `config.json` beside its root filesystem, for one thing: the supervisor reads the image's own `PATH` from it and a box gets that search path. Nothing else of the image config is used (not its user, not its entry point).
- The proxy unit tests use a TCP echo for the tunnel, not a TLS server: a CONNECT tunnel is opaque bytes to the proxy.
- CI: a manual workflow (`.github/workflows/box-tiers.yml`), not a job in `ci.yml`. It has not run on a hosted runner, and a job that may not be able to run runsc must not gate a pull request.
- The worker end to end suite covers a Bash turn, a reply through the shims, isolation, abort, drain and restart, and the failed start. **It does not cover** a denied hook, a bridged MCP call or an upload from the scratch directory in a boxed session.
- The gateway cannot pin a session in that suite (the box tables are Postgres only), so the box in the bundle and the pin in the session view are added to what the node's client reads. Everything after that is the production path.

## Not verified

- **A cluster.** Kill criterion K1 is still open: nothing here ran in a pod. The nested stage is a privileged Docker container with its own cgroup namespace and a 4 GB limit; there the supervisor's cgroup delegation worked, the supervisor reported the container's memory limit and the node's sizing check refused a budget above it.
- **A real model and a real provider.** The provider proxy was exercised against the mock model and a local recorder only. Whether the OAuth token form works behind it against the real provider is as open as it was after phase 0.
- **K2c.** No performance number was taken here. The owner's decision between gVisor and bwrap still needs the real-model turn of the phase 0 note; both tiers pass the same contract, so the decision is a configuration value.
- **amd64.** Everything ran on aarch64. The amd64 checksum of the runsc release in the Dockerfile was computed from the published archive and matches its published SHA-512, but no amd64 binary was run, and the amd64 system call numbers of the seccomp filter are checked only by the table test.
- **The whole image.** The box layers of the Dockerfile were built and used (the nested stage); the full image was not built.
- **Packs through the supervisor on Linux with an object store.** The packer over the supervisor's protocol is tested with a local directory on macOS; `hm` and `wx` were not flushed to or hydrated from an S3-compatible store through a real supervisor, and `tests/integration/box-resume.test.ts` is still not written.
- **An allowlisted public host from a box.** Refusals were shown end to end; the allow path was shown against local servers only.
- **Long runs.** Nothing ran for more than minutes: no soak, no density under load, no memory pressure with real boxes.
- **A node worker that is not root.**
