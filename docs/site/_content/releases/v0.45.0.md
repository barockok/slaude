## v0.45.0 — personas that carry their own credentials, nodes that prove who they are, and MCP that never leaves the gateway (draft for the RC series)

> [!NOTE]
> **Draft for `v0.45.0-rc.1` and later.** This release changes the database
> schema (three additive columns and one table), node authentication, the queue
> topology, the runtime-bundle contract and the agent loop, so it goes out as
> release candidates first (`SLAUDE_VERSION=0.45.0-rc.N`). These notes are kept
> under the stable name and updated as each RC adds scope. If v0.44.1 is not cut
> separately, its notes ([v0.44.1](v0.44.1.md)) fold into this release.

The theme is moving per-agent decisions to the gateway. In the gateway and node
topology an agent's identity, provider credentials, MCP servers and knowledge
scope are defined once (in git, through personas as code), resolved on the
gateway, and delivered to a node only as far as the node needs them. Nodes in
turn prove which agents they may serve. Each feature is inert until configured.

### Features

- **Provider credentials by reference (WS-A).** A persona can declare its own LLM
  provider as references: `vault://<mount>/<path>#<field>` (HashiCorp Vault KV v2)
  or `env://PERSONA_<NAME>`. The gateway resolves them when it builds the runtime
  bundle, at session start, resume and reload; a key rotated in Vault is used by
  the next **new thread** (after the gateway's 60 s cache), and `/reload` applies
  it at once. `provider` is one atomic set, so a persona's `baseUrl` only ever
  receives the key declared beside it. A failure is fatal and typed
  (`PROVIDER_CREDENTIALS_UNAVAILABLE`, one fixed Slack message per job), never a
  silent fallback. Vault configuration is gateway-only: Kubernetes auth with a
  projected token on the gateway pod, a required allowlist with a `{persona}`
  segment, and nodes refuse to boot with any Vault variable. `mono` refuses
  provider references and Vault. See [Provider credentials](../deploy/provider-credentials.md)
  and the [field note](../field-notes/2026-10-05-provider-credentials-by-reference.md).
- **Node credentials, labels and routing (WS-B).** A node authenticates with a
  signed credential (`bun run node-token mint|inspect|revoke`, key
  `SLAUDE_NODE_KEY`) carrying its labels; a persona runs on the label in its
  `runsOn`. Each label has its own queue (`turns` for `default`,
  `turns.label.<label>` otherwise), the label is signed into every job token, and
  every persona-scoped `/v1` route refuses a node without it (`403 this node may
  not serve this agent`), counted by `slaude_gate_denied_total{route}`. A relabel moves pending messages and re-dispatches an
  in-flight turn once. A label with waiting turns and no live node is reported
  (`slaude_label_unserved`, `GET /panel/api/labels`). Credentials expire, can be
  revoked by id and rotated with `SLAUDE_NODE_KEY_PREVIOUS`; the legacy shared
  token still works and can be closed with `SLAUDE_NODE_LEGACY=off`. The reaper
  now rescues a dead node's **claimed** warm-routed turn, which before stayed
  active forever. See [Multi-node deployment](../deploy/multi-node.md) and the
  [field note](../field-notes/2026-10-05-node-labels-and-routing.md).
- **Node-local stdio MCP manifest.** A node runs stdio MCP servers only as
  declared in `SLAUDE_NODE_MANIFEST` (default `/etc/slaude/node.json`), per
  persona, keyed on the verified job claims. See [Node MCP manifest](../deploy/node-manifest.md).
- **The MCP bridge (WS-C).** A managed persona's remote HTTP MCP servers work on
  nodes: the bundle carries server names only, and every call goes through the
  gateway, which chooses the agent's or the person's credential per call and
  refreshes tokens. Credentials never reach a node. See [MCP bridge](../deploy/mcp-bridge.md).
- **Knowledge scope (WS-C).** `kbSources` limits which knowledge bases a persona
  reads, enforced on the gateway for every KB tool; `list_kbs` and `search_kbs`
  are filtered and no longer return disk paths. A filter, not isolation. See
  [Knowledge scope](../deploy/knowledge-scope.md) and the
  [field note](../field-notes/2026-10-05-persona-config-on-nodes.md).
- **Episodic memory for node turns runs on the gateway**, in the persona's own
  slice. Before, a node wrote every persona's transcripts, 1:1s included, into one
  `agent-default` slice.
- **Per-request Slack client.** In HTTP mode every outbound call goes out as the
  app the session belongs to, not the oldest registered app; two apps in one
  channel no longer answer each other.
- **Payload versions.** `personas render` writes `version` 2 for `provider` or
  `runsOn` and 3 for `kbSources`, so an older gateway refuses a payload it would
  otherwise misread.
- **Voice mode.** The agent can join a live call in a workbench browser tab and
  talk. A realtime voice model (OpenAI Realtime or Gemini Live, set by a
  provider-qualified `SLAUDE_VOICE_MODEL`) handles the audio; anything needing
  facts or tools is handed to the thread's own Claude session and the answer is
  spoken back. Why two models: realtime turn-taking needs sub-second latency a full
  agent turn cannot give, and delegating keeps persona, memory, tools and
  credentials on the session. Four tools (`voice_start`, `voice_say`,
  `voice_context`, `voice_stop`); the thread is quiet during the call and a
  summary plus transcript file arrive at the end. Calls run as the agent only:
  refused in `/1on1`-locked and `/remote` threads, identity re-checked before
  every injected turn, call ended on a change. Off unless `SLAUDE_VOICE_ENABLED=1`.
  It touches the agent loop, so it ships in `v0.45.0-rc.1` first. Under the
  normal permission mode starting a call asks for approval; the mid-call
  controls do not.
  In the gateway topology the gateway holds the `SLAUDE_VOICE_*` variables and
  ships a voice block in the runtime bundle; `SLAUDE_VOICE_TENANTS` (a list or
  `*`; unset means none) picks the tenants that receive it, so the one voice key
  never reaches other tenants' nodes. Needs a workbench with browser audio and
  the `stream_token` capability. See the [guide](../guides/voice-mode.md) and
  the [field note](../field-notes/2026-10-08-voice-mode.md).
- **GPT-Live voice provider (`openai-live`).** A third voice adapter for OpenAI's
  GPT-Live (`SLAUDE_VOICE_MODEL=openai-live/gpt-live-1`). Why: it is full duplex,
  and its client-delegation mode hands the model's requests to our application,
  so Claude stays the brain; the hosted-tools mode was rejected because it would
  put an OpenAI model in front of Claude. It is a lossy fit: no truncate or
  cancel, turn events synthesized from quiet gaps, and a call cannot end itself
  by voice (leaving goes through Claude's `voice_stop`). See the guide's
  GPT-Live section.

### Behaviour changes to read before upgrading

> [!WARNING]
> **Two refusals are now the default.**
> - **A node pod that still loads the gateway Secret does not start.**
>   `SLAUDE_NODE_BOOT_CHECK` defaults to `refuse` (v0.44.1 warned): a node whose
>   environment holds any gateway-only variable exits at boot, naming the
>   variables. Finish the Secret split before rolling nodes to this release, or
>   set `SLAUDE_NODE_ALLOW_GATEWAY_SECRETS=1` on the node as a temporary escape
>   (or `SLAUDE_NODE_BOOT_CHECK=warn`).
> - **A `/deploy` payload with a field the gateway does not know is refused**
>   (422, naming the field). `SLAUDE_DEPLOY_STRICT` defaults to on. Upgrade the
>   gateways before the pipeline that renders new fields; `SLAUDE_DEPLOY_STRICT=0`
>   on the gateway restores "ignore and report in `ignoredFields`".
>
> The security switches (`SLAUDE_NODE_LEGACY`, `SLAUDE_NODE_ALLOW_TOKENLESS_PENDING`,
> `SLAUDE_DEPLOY_STRICT`, `SLAUDE_NODE_BOOT_CHECK`, `SLAUDE_NODE_ALLOW_GATEWAY_SECRETS`)
> share one spelling (`1`/`true`/`yes`/`on`, `0`/`false`/`no`/`off`), and an
> unknown value refuses the boot, naming the variable. Before,
> `SLAUDE_NODE_LEGACY=0` silently left the legacy door open.

- **Outbound policy.** MCP OAuth discovery, registration, code exchange and
  refresh, and every MCP bridge request, now refuse `http` and private,
  shared, link-local and metadata addresses, and follow no redirects. In-cluster
  identity providers and MCP servers (and tailnet hosts) must be listed in
  `SLAUDE_OUTBOUND_INTERNAL_HOSTS` on the gateway, by exact hostname, or their
  flows fail. Stored credentials are kept; listing the host and restarting
  recovers them. See [Outbound fetch policy](../reference/configuration.md#outbound-policy).
- **The agent child's environment is scrubbed** of every gateway-only variable,
  `SLAUDE_NODE_TOKEN`, `SLAUDE_REDIS_URL` and the brain's embedding provider keys
  (`OPENAI_API_KEY`, `VOYAGE_API_KEY`, `ZEROENTROPY_API_KEY`,
  `GOOGLE_GENERATIVE_AI_API_KEY`, `OPENROUTER_API_KEY`, `MINIMAX_API_KEY`,
  `TOGETHER_API_KEY`), in every role. The same list is refused as a node
  manifest `env` key and left unexpanded in a `.mcp.json` placeholder: an MCP
  server that needs one of these keys must read it under another name. In `mono` this
  removes the Slack tokens and the database URLs from the agent child: a skill or
  tool that read `SLACK_BOT_TOKEN` or `SLAUDE_PG_URL` from its environment no
  longer finds it.
- **Nodes mount no plugin or stdio MCP server unless the manifest declares it.**
  A node without `SLAUDE_NODE_MANIFEST` (default `/etc/slaude/node.json`) runs no
  stdio or plugin MCP server for any persona, and every node agent child runs
  with `strictMcpConfig`, so a project `.mcp.json` is not read. `mono` is
  unchanged.
- **The node boot check.** A node with a gateway-only variable refuses to boot
  by default (`SLAUDE_NODE_BOOT_CHECK=refuse`) unless
  `SLAUDE_NODE_ALLOW_GATEWAY_SECRETS=1`; `SLAUDE_NODE_BOOT_CHECK=warn` only logs.
  A node with any Vault variable always refuses.
- **`/v1/pending` without a job token** is accepted only from the legacy identity
  while `SLAUDE_NODE_ALLOW_TOKENLESS_PENDING` is on (default on, for this
  release).

### Upgrade order and rollout

1. **Gateways first, then nodes**, for every step.
2. The **node image must be at this release before the new node Secret is
   applied**, and **queued and running turns must drain first**
   (`slaude_queue_depth` at 0): a job minted by an older gateway carries no
   `lock` claim and fails on a node with no database.
3. Configure features one at a time, and only after **every** node runs this
   release: provider references, then node credentials
   and labels (one node Deployment and one KEDA ScaledObject per label, at least
   two replicas each), then the bridge and KB scope.
   An older node ignores `ownProvider`: it fills the fields a persona left out
   from its own environment, so the persona's resolved key goes to the node's
   own `ANTHROPIC_BASE_URL`, a host the persona never named. Set provider
   references only after every node is upgraded.
   **docker compose `scale` profile:** the worker no longer loads the
   gateway's `.env` (it would refuse to boot: that file holds Slack tokens and
   `SLAUDE_JOB_SECRET`). Copy `.env.node.example` to `.env.node` with only the
   node's variables (`SLAUDE_NODE_TOKEN`, provider variables as the node-env
   fallback) before upgrading; `SLAUDE_NODE_ENV_FILE` names another file.
4. Close the legacy door (`SLAUDE_NODE_LEGACY=off`) once every node has a signed
   credential and `slaude_node_legacy_auth_total` stays flat.

**What changed in `deploy/k8s-scale`.** If you apply the shipped manifests, read
the diff first: `SLAUDE_NODE_TOKEN` moved out of `slaude-scale-node-secrets`
into one credential Secret per node deployment (`slaude-scale-node-cred-default`,
`slaude-scale-node-cred-finance`), read by key (the order is below); the node
deployments set `SLAUDE_NODE_BOOT_CHECK=refuse` and
mount an empty stdio manifest at `/etc/slaude/node.json`; `slaude-node-finance`
is an example second label (delete it, its PDB, ScaledObject, fallback HPA and
credential Secret if you run one label); the gateway loads a new gateway-only
ConfigMap (`slaude-scale-gateway-config`: Vault, off until `SLAUDE_VAULT_ADDR`
is set; `SLAUDE_OUTBOUND_INTERNAL_HOSTS`; the legacy door) and mounts a
projected ServiceAccount token for Vault; the gateway Secret template carries
`SLAUDE_NODE_KEY`, which a gateway needs only to verify (and the CLI to mint)
**signed** node credentials: without it the legacy token stays the only door,
so leave it out until you mint the first signed credential; the CPU fallback
HPAs moved to `optional/node-cpu-fallback-hpa.yaml` (apply it instead of
`70-autoscale.yaml` where KEDA is absent, never both); the optional NetworkPolicy selects node pods by
`slaude.dev/tier: node`, a label only the new node pod templates carry.
`slaude-node` keeps its selector, so it updates in place.

Moving `SLAUDE_NODE_TOKEN` into the credential Secrets, in this order:

1. **Drain first**: stop new work and let queued and running turns finish
   (`slaude_queue_depth` at 0).
2. **Node image at this release first**: an older node does not read the
   credential Secret.
3. **Create the credential Secrets** before anything else changes:
   `slaude-scale-node-cred-default` holding the node's **existing**
   `SLAUDE_NODE_TOKEN` value (the legacy token; the gateway keeps accepting it
   as `SLAUDE_NODE_LEGACY_TOKEN` while the legacy door is open), and one per
   further label holding a newly minted signed credential.
4. **Apply the new `50-node.yaml`** (node deployments that read the credential
   by key), and only **then** the new `10-secrets.yaml`.

Do not apply the new `10-secrets.yaml` before the new `50-node.yaml`: it removes
`SLAUDE_NODE_TOKEN` from `slaude-scale-node-secrets`, so a node pod still on the
old template that restarts in between starts with no credential and cannot reach
the gateway.

The alerts to wire up before relying on any of this are in the
[alerts runbook](../deploy/alerts.md).

### Exposed secrets: rotate after the Secret split

Any cluster that ran nodes with the shared Secret (before the split) must treat
`SLAUDE_JOB_SECRET` and `SLAUDE_MASTER_KEY` as **exposed** to every node pod and
every agent turn that ran on one, together with the database passwords, the
Slack client and signing secrets and `SLAUDE_OAUTH_STATE_SECRET`.

- `SLAUDE_JOB_SECRET`: drain the queues, write a new value into the gateway
  Secret, restart the gateways. Nodes never hold it.
- `SLAUDE_MASTER_KEY`: **rotation is not supported in this release.** No tool
  re-encrypts stored credentials under a new key. Changing the key makes data
  encrypted under the old key fail to decrypt, and a gateway serving a managed
  tenant can fail at boot. The procedure is to discard the stored credentials and
  re-enter them (re-run onboarding, `/mcp connect` and the provider setup), after
  a backup; or keep the key and record the exposure (finish the split so it stops
  reaching nodes). The full procedure is in
  [What nodes were exposed to](../deploy/multi-node.md#what-nodes-were-exposed-to).
  A re-encryption tool is a follow-up planned before the stable release.

Rotating any of these is an explicit decision for the operator, not a step of
the upgrade.

### Rolling back after configuring

Each feature is inert **until configured**, which makes an RC safe to install.
It does not make a configured cluster safe to roll back. Older code ignores the
new settings:

| What was configured | What older code does after a rollback |
|---|---|
| `provider` references | ignores the column; managed personas fall back to node-environment credentials |
| `runsOn` | ignores it; every persona runs on `default` |
| `kbSources` | ignores it; every persona regains all knowledge sources |
| node credentials | older gateways reject them (401); nodes must go back to the static token |

Remove the references, labels and KB lists through a sync before rolling back,
or accept the table. The procedure and the rehearsal are in the
[rollback runbook](../deploy/rollback.md).

### Known issues

- **The gateway reads `.env` and `.mcp.json` from the shared volume** nodes can
  write. A node turn can set a gateway variable for after a restart, and
  `.mcp.json` placeholders can expand any non-gateway-only gateway variable.
- **Runtime soul overrides on nodes** apply only when the bundle carries the
  structured soul.
- **The `lock` claim in a job token can be stale** for a job that waited while
  the lock flipped; it is corrected on the next job.
- **A node paused on a refused credential stays live** (`/healthz` 200) and is
  not ready; alert on `slaude_node_auth_paused`.
- **Only the dispatching gateway re-dispatches** a `LABEL_MISMATCH` turn; if it
  restarts first, that turn ends with no reply. Two message-ordering races remain
  (documented under [Moves are at-least-once](../deploy/multi-node.md#moves-are-at-least-once)).
- **The node-side MCP credential seeding** stays until the bridge has run on a
  cluster. The bridge's connect-card rate limit, and failure-message
  de-duplication, are per process.
- The manifest wrapper assumes Linux (`--config=/dev/null`); runtime-control keys
  (`NODE_OPTIONS`, `LD_PRELOAD`, ...) are not yet refused as manifest `env` keys.

### Fixes

- A dead node's claimed warm-routed turn is now recovered by the reaper.
- A job token's total life is capped (`SLAUDE_JOB_TOKEN_MAX_AGE`, 6 h) and a
  long-queued job gets a new token only within `SLAUDE_JOB_MAX_AGE` (24 h).
- `/v1/pending` answers only the caller's own session.
- The `/1on1` lock reaches nodes as a signed claim, not a database read.
- `/bash` is refused on a gateway (it ran next to the master key, the job
  secret and the node key, and posted the output to Slack). In `mono` it runs
  with the agent child's environment scrub, so `/bash env` shows no
  gateway-only variable.
- Episodic memory in `mono` is scoped by each turn's own context, as node turns
  are through the gateway: a named persona's turns land in its own slice (they
  used to land in the default persona's, 1:1s included). On both paths a job
  that runs as a person (a cron created inside a 1:1) uses that person's slice,
  and a manager speaking in someone else's locked thread reads and writes no
  memory at all. In `mono` the scope follows the route's current speaker when
  the memory call runs: a later message from someone else can re-scope an
  earlier turn's write, which then fails closed or stays in the same thread.
- Token refresh and reissue accept a moved job's held copy (it runs under a new
  id with the original token) by following the `job-moved` marker, only when
  the copy stores the presented token. Forging a marker is moot rather than
  impossible: it needs Redis write access, and Redis already holds every queued
  job's token.
- The MCP OAuth error path no longer carries a pinned private address into Slack.
- Voice workbench endpoints are model-supplied, so they must be same-origin with
  the configured workbench URL and carry no credentials; otherwise a
  prompt-injected endpoint would receive the stream token.
- Voice: the mid-call tools (`voice_say`, `voice_context`, `voice_stop`) no
  longer post an approval card during the call, and every approval card now
  redacts secret-named keys and route-header values, so `voice_start`'s card
  (it still asks) does not print the stream token into the thread.
- Voice: `SLAUDE_VOICE_API_KEY` is gateway-only. Before, the agent child in
  `mono` (which runs Bash, on requests that came from speech) and the
  brain-think child inherited it.
- Voice: a late `now` reply is downgraded to the next pause as designed (the
  staleness stamp was always current); a failed or hung workbench clear no
  longer ends or freezes the call; an uplink lost mid-call ends it
  `audio_lost` instead of leaving the agent mute; a node voice turn's events
  stay out of the thread; `mono` shutdown ends live calls.
- The job-token refresh response now carries the thread's current identity, so a
  slash-only `/1on1` or `/remote` change (which does not reboot a node's session)
  is seen by an active call.
