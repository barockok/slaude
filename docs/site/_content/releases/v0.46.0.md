## v0.46.0: agents with their own access rules, an audit trail, a new console, and proactiveness with one switch (draft for the RC series)

> [!NOTE]
> **Draft for `v0.46.0-rc.1` and later.** This release changes the database
> schema (two new tables, `audit_events` and `agent_grants`, in migration
> `0032` with a sqlite mirror) and who may decide a tool permission card, so it
> ships as release candidates first.
>
> It also changes the agent loop (proactive wakes, and how a message waits for
> a running skill check) and what `Enabled: yes` under Proactive means. The
> first candidate was `v0.46.0-rc.1`; `v0.46.0-rc.2` adds the console session
> fixes below and also changes what the agent remembers of a turn;
> `v0.46.0-rc.3` is a console polish pass from a live smoke test of the new
> console (no schema change); `v0.46.0-rc.4` adds the console's Resources
> section (Skills and Guardrails), rendered markdown and surface-neutral
> console words (no schema change); `v0.46.0-rc.5` fixes the brain's embedding
> model labels and refuses to embed with a model the brain was not built for
> (no schema change); `v0.46.0-rc.6` fixes four findings from a live smoke of
> the console and portal (no schema change); `v0.46.0-rc.7` turns the
> Guardrails page into a view of the runtime's own layer and marks each SDK hook
> with a registry id (no schema change; the agent loop's hooks are unchanged);
> `v0.46.0-rc.8` closes the two node behaviour gaps rc.7 found: node workers
> now install the must-reply Stop guard and refuse every tool in a wake
> (no schema change); `v0.46.0-rc.9` adds owner-defined guardrails (schema
> change: three new tables in migration `0033` with a sqlite mirror; the agent
> loop gains two PreToolUse hooks, an inbound drop and a Guidance block; a
> `/deploy` payload may now be version 5) (`SLAUDE_VERSION=0.46.0-rc.N`).
> These notes are kept under the stable name and updated as each RC adds scope.

Until now a persona was an identity whose job lived in SOUL.md prose, and most
access decisions read only the default persona's soul. A named persona
admitted, and asked for approval from, whoever the default persona would. Any
viewer of a tool permission card could approve it, and approvals left no
durable record. This release gives each agent its own access rules, records
every decision, and replaces the panel and portal with a console built on the
same vocabulary as the Claude platform's agent console (agents, sessions,
environments, memory). The design and the mapping are in the
[agent platform field note](../field-notes/2026-11-07-agent-platform.md).

It also makes proactiveness one setting. Turning it on used to take several
settings and a checklist page, and agents that had it on did not finish work:
over three days a live deployment produced 11 posts, all concepts or status. A
wake could not see replies, could not save to memory, lost its mandate after a
soul edit, and a new thread started with no idea what the agent had been
doing. Now `Enabled: yes` in a place is enough, the mandate is the job, and a
wake reads Slack before it thinks. The measurements and the fixes are in the
[proactive simple field note](../field-notes/2026-11-03-proactive-simple.md).

### Behaviour changes to read before upgrading

- **A persona whose SOUL.md says `Enabled: yes` under Proactive starts working
  unattended after upgrade (one switch now enables wakes). Set `Enabled: no`
  before upgrading if you do not want that.** This holds for the global
  `## Proactive` section and for a `### Proactive` block inside a
  `## Channel` block, as long as the persona has a manager. Before, a wake
  also needed `Wake: yes` and `Highest: act`. The mandate is now the job and
  the authority: `Wake: no` keeps a persona on the summarising round, and
  `Highest`, `Cooldown` and the old cap name still parse but only narrow.
- **Proactive defaults are wider.** Where proactiveness is on: the ceiling
  (`Highest`) defaults to `act` (was `inform`), the cooldown between posts to
  one recipient to 1 hour (was 4), and the daily cap per recipient to 6 (was
  1). `Max per day` is accepted in the global section and `Max per person per
  day` in a channel block. A proactive post may be up to 3000 characters (was
  1200).
- **`self/heartbeat` is optional.** The persona's mandates plus that page are
  the job, and a change to either wakes the agent. A wake that does not say
  when to look next sleeps 4 hours (was one scheduler slot).
- **`proactive_post` takes `text` and little else.** `level` is gone:
  `needs_reply: true` asks and waits for an answer. `destination` may be left
  out when the agent works in one place, and `kind`, `evidence` and `item_id`
  are optional.
- **A wake may add one follow-up to a thread until someone answers.** In a
  wake, `post_message` works in the thread of any post the agent made (it was
  only posts made in the same wake), and is refused once the agent has left
  two messages in a row there. The count is read from the thread itself.
- **`read_channel` reads the channels the agent works in** as well as its
  `Read:` list, and takes `thread_ts` to read one thread.
- **Tool permission cards need the requester or an approver.** A click on a
  permission card is accepted only from the person whose message started the
  turn, the thread's `/1on1` lock owner, or a user with the approver or manager
  role on the persona. Anyone else gets an ephemeral note and the card stays
  pending. Turns with no single human sender (cron, heartbeat, background,
  console chat, or several people posting in one turn) need an approver or
  manager. Cards opened before the upgrade carry no requester and need an
  approver or manager.
- **The backup manager passes the `/heartbeat` and `/1on1` manager checks.**
  Every role check now goes through one function, and the backup manager holds
  the manager role there.
- **Global approvers lose admin commands in channels with their own approvers.**
  In a channel whose `## Channel` block names its own approvers, only those
  approvers (and the managers) hold the approver role. A global approver keeps
  admin commands everywhere else. Before, admin commands read the global list
  in every channel.
- **A named persona's approval card never falls back to anyone.** Its
  approvers are its users with the approver or manager role; with none, the
  default persona's managers. The legacy approver list, `SLAUDE_APPROVERS` and
  "anyone may click" stay fallbacks of the default persona only. With no
  manager anywhere nobody may approve and the card times out denied.
- **Audit stdout line format changed.** The panel's operator action line was
  `{"evt":"panel.audit",...}`; every audit line is now `{"evt":"audit",...}`
  with `id`, `action`, `actor_kind`, `actor_id` and, when present, `persona`,
  `target_kind`, `target_id`, `decision`, `session`, `channel`, `thread_ts`,
  `summary` and `detail`. Update log queries and alerts that match
  `panel.audit`.
- **Deny grants apply to the default persona's approval cards.** A user with
  a deny grant (a stored deny or a SOUL.md blocked user) is dropped from the
  card's approver list even when SOUL.md, the legacy list or
  `SLAUDE_APPROVERS` names them, and is refused at click time on a card anyone
  may decide. If the deny removes everyone the list named, nobody may approve.
- **Console roles are superadmin only.** `GET /panel/api/console-roles`
  returns `403` to an operator; the Access page shows operators a note
  instead of the allowlist.
- **Channel grants take channel ids only.** A channel subject must start with
  `C` or `G`. A DM id (`D`) is refused: give the person a user member grant
  with DM only instead.
- **Personal and profile memory stores are superadmin only** in the console.
  Operators do not see `user-*` and `profile-*` stores, get `403` on their
  pages, and each page a superadmin opens in one is audited.
- **Metric label change.** `slaude_v1_tool_calls_total` counts a memory tool
  under its `memory_*` name and gains an `alias` label (`true` when a node
  called the old `kb_*` name). Dashboards grouping by `tool` see the new names.
- **New environment variables.** `SLAUDE_AUDIT_RETENTION_DAYS` (default `365`)
  bounds how long audit events are kept. `SLAUDE_MEMORY_TOOL_ALIASES`
  (default `1`) set to `0` stops offering the `kb_*` tool aliases; leave it on
  while sessions started before the upgrade may resume.
- **Web apps moved to `src/web`.** The console builds to
  `src/web/console/dist` and the portal to `src/web/portal/dist` (they were
  `src/gateway/panel/web/dist` and `src/gateway/portal/web/dist`). The
  Dockerfile, `panel:build`, `portal:build` and `web:build` are updated; a
  custom image or build script that copies the old paths must change. The URLs
  (`/panel/`, `/portal/`) and every JSON API are unchanged.

### Features

- **A structured soul per persona.** A named persona's managers, channels, DM
  allowlist, blocked users and approvers now come from its own synced
  `soul_json`. Each of those is one unit: a persona that names any part of a
  unit takes it whole from its own soul, otherwise whole from the default
  persona. This keeps the guarantee the admission tests pin: with no stored
  grants, a persona admits exactly what it admitted before. Filesystem
  personas have no structured soul yet and keep the default persona's units.
- **Agent grants.** A grant gives a user, a channel's members or a whole
  workspace the `member`, `approver` or `manager` role on one agent, or denies
  a user (a deny always wins). Grants derived from the soul are computed in
  memory; superadmins add and revoke stored grants in the console. Approver is
  an approval right only: it never lets someone chat with the agent. A grant
  read failure falls back to the soul alone and counts in
  `slaude_grants_read_failures_total`, so a database blip never drops a
  manager.
- **One role function.** `roleOf(persona, user, channel)` answers every role
  check (`/1on1`, admin commands, `/heartbeat`, agent admin tools, proposals,
  the approval gate) for the persona the turn runs as, on nodes too.
- **Audit trail.** One writer records to `audit_events` and to stdout,
  redacted the same way approval cards are. A failed write never blocks the
  decision; it counts in `slaude_audit_write_failures_total`. Read it at
  `GET /panel/api/audit` and `GET /panel/api/sessions/:id/audit`. The actions:
  - gates: `gate.permission.decided|refused|expired|cancelled`,
    `gate.approval.decided|refused|expired|cancelled`,
    `gate.mcp_connect.decided|expired` (`gate.*.expired` also comes from the
    pending sweep, actor `system`);
  - `grant.created|revoked`, `proposal.decided`, `ignore.set|cleared`,
    `one_on_one.locked|unlocked`, `soul.override.set|cleared`,
    `persona.sync`, `memory.page.viewed`;
  - console sign-in: `panel.auth.login|denied|refresh|logout`;
  - console actions: `panel.session.control`, `panel.config.reload`,
    `panel.persona.onboard`;
  - console refusals (decision `refused`): the console actions above plus
    `panel.persona.override`, `panel.grant.create|revoke`,
    `panel.memory.private` and `panel.console.roles.read`. An applied console
    override is recorded as `soul.override.*`.
- **Mandates.** The console lists each agent's jobs: the soul's mandate, each
  channel block, each cron and the heartbeat, with triggers and the approvers
  who can actually approve at runtime (the same resolution the approval gate
  uses).
- **The console** (served at `/panel/`): Overview, Agents (overview, mandates,
  access, activity), Sessions (timeline, chat, audit), Approvals and audit,
  Access, Memory (stores, pages, read only) and Environments (node pools,
  placement, personal environments without secrets). Light and dark themes
  on one set of design tokens.
- **The portal** (served at `/portal/`): My account (linked Slack identities),
  Integrations, and My agents (the agents a person holds a grant on, with the
  role).
- **Memory tool names.** The agent's memory tools are `memory_save`,
  `memory_search`, `memory_think`, `memory_get`, `memory_list`,
  `memory_delete`, `memory_graph`, `memory_thread_history`, `memory_stores`
  and `memory_search_stores`. The `kb_*` names (and `list_kbs`, `search_kbs`)
  stay as aliases because a resumed session keeps calling the names it saw.
  `SLAUDE_AUTO_ALLOW_TOOLS` and the profile write guard accept either name,
  and the `kb` and `kb-admin` approval categories are unchanged.

- **Proactiveness with one switch.** `Enabled: yes` in a place turns it on;
  everything else has a default (see the behaviour changes above).
- **Wakes see what happened.** Before the model call, code reads up to three
  days of each working channel (and its `Read:` channels): new messages, new
  replies in active threads, and for each of the agent's recent posts the
  replies it got or `NO ANSWER after Nh`. A read failure is stated in the
  block, never read as silence. The wake prompt says what counts as finished
  work and what does not.
- **New threads know the agent's own work.** The first turn of a thread in a
  place where the agent works on its own gets its recent posts there, its
  latest notes and its work folder, as data.
- **`/heartbeat now`.** The manager (or anyone holding the manager role on the
  persona) can make the agent look at its work now. It goes through the
  normal path: budget, caps and restraint are unchanged.

**Resources and surfaces (rc.4):**

Operators could see what an agent did but not what it can do or what holds it
back: skills arrived from four places (the manifest, plugins, slaude itself
and the agent's own `write_skill`) with nothing listing them together, and the
limits on an agent were spread over environment variables, the soul, grants,
learned rules and constants in the code.

- **Resources > Skills.** One list of every skill an agent can use, with its
  source (built-in, installed, plugin or agent-authored), where it came from
  (repository and pinned commit from `slaude.lock`, plugin and version, or the
  agent that wrote it), which agents have it, its uses from `skill_usage`, and
  whether it is retired. A skill's page shows its `SKILL.md`, files, per-agent
  usage and related proposals. A superadmin can retire a skill the agent
  wrote itself, or restore a retired one, through the weekly review's own
  path; both are audited (`skill.retired`, `skill.restored`). API:
  `GET /panel/api/skills`, `GET /panel/api/skills/:id`,
  `POST /panel/api/skills/:id/retire|restore`.
- **Resources > Guardrails.** For each agent, every guardrail family with its
  effective values and where each comes from (env, soul, persona config,
  console grant, learned rule, default, or fixed in code): tool permissions,
  approvals, admission and grants, memory write gating, the profile write
  guard, redaction, proactive restraint and learned rules, the wake tool
  allow-list and budgets. Read only. API: `GET /panel/api/guardrails?agent=`.
  Policy guardrails are listed as designed but not implemented.
- **Markdown, rendered.** Memory pages, `SKILL.md` files, mandate text, the
  soul's guardrail sections and agent messages in the session timeline and
  chat render as markdown, each with a Rendered or Raw switch (remembered per
  viewer) and a copy button. The renderer is written in-repo and builds React
  elements from a parsed tree: raw HTML is never passed through, and only
  `http`, `https` and `mailto` targets become links.
- **A console that is not tied to Slack.** Session views, history lines, live
  user messages and audit events carry a `surface` (`slack` today), and the
  console takes its words from a small surface registry ("in Slack", "Sent to
  Slack", "No thread"), so another chat surface needs a registry entry rather
  than a console rewrite. Slack-only features (grants, an agent's Slack user,
  `/env`) still say Slack.
- **Each agent's own redaction and approval timeout.** A named agent's own
  redaction patterns were ignored, and its approvals waited for the default
  soul's timeout. Redaction is now the default soul's patterns **plus** the
  agent's own (a union: an agent's soul can only add redaction, never remove
  the default's). The approval timeout is the agent's own when its soul sets
  one, else the default's as before. **If a named agent's soul lists
  redaction patterns, they are now applied to its replies, in addition to the
  default's.** The guardrails page shows pattern values to superadmins only;
  operators see a count.
- **Names instead of ids.** The agent Access tab and the Access page show
  grant subjects as channel, user and workspace names (ids beneath). The
  portal's account and My agents pages, and the `/portal/link` confirmation
  page (now styled with the console's design tokens), show the workspace and
  Slack user names. Workspace names come from `auth.test` of that
  workspace's own bot token, so no new Slack scope is needed. The link page puts
  every value in escaped attributes (never in its script) and is served with
  a strict Content-Security-Policy (`default-src 'none'`, a per-response
  nonce for its one style and one script). The skills API reads `SKILL.md`
  only as a regular file inside the skill's directory, up to 256 KB.
- **Linking guidance that works.** "Run /link in Slack" failed, because Slack
  rejects a message starting with an unregistered slash command. The portal
  and docs now say to send `/link` to the agent as a message, in Slack with a
  space before it or after mentioning the agent. The Slack app manifest
  still registers no slash commands: the gateway has no slash-command route.
- **Approval cards say what was approved.** A request with no category read
  "Plan → Approved" and was audited with target `plan`; both now use the
  request's category, else the first line of its summary.
- **Heartbeat wakes and scheduled runs are labelled** "Heartbeat wake" and
  "Scheduled run" in the session list and header.
- **Skill moves are audited everywhere.** `skill.retired` and
  `skill.restored` are recorded for the weekly skill review and the Slack
  Restore button too, not only the console, and a console retire records the
  operator (not `skill-review`) as its decider. Plugin skill uses count under
  every name the runtime records them by.

#### rc.9

**Owner-defined guardrails (phase A1).** The Guardrails page showed the
runtime's own layer, the same for every agent on every deployment, and nothing
on it was the owner's. Now a guardrail is the owner's resource, like a soul or
a skill: a `GUARDRAIL.md` in the deploy repo's `guardrails/` folder (or host
files imported with `slaude guardrails import <dir>`), shared by every agent
or for some, narrowed to channels. See the
[owner guardrails field note](../field-notes/2026-11-08-owner-guardrails.md)
and the [guardrails reference](../reference/guardrails.md).

- **Enforced rules, checked by code and never put in the prompt.** Tool rules
  deny or record a tool call in threads, wakes, remote threads and background
  passes, in every permission mode, bypass included. Inbound rules drop a
  message before any turn and reply once per person per thread per ten
  minutes with the rule's message. A tool rule that asks for approval is
  enforced as a deny until approval cards arrive (rc.10); reply rules are
  stored and shown as *Not yet enforced* until the single outbound choke point
  (rc.10). Patterns run on a linear-time engine (`re2js`); tool input is
  matched per field, never as serialised JSON.
- **Guidance, advisory text the agent reads.** With `load: always` it sits
  after the soul in the system prompt, within a per-agent cap
  (`SLAUDE_GUARDRAIL_PROSE_MAX`, 4000 characters; a guardrail that does not fit
  is left out and named in the console). With `load: on-match` only its name
  and description are in the prompt, and code hands over the text once per
  session when a tool or message trigger matches.
- **The database is the only runtime source, and it is signed.** Three tables
  (`guardrails`, `guardrail_overrides`, `guardrails_manifest`) in Postgres and
  sqlite. Every row is signed, and one manifest row signs the whole set, so a
  deleted, replayed or added row fails the check; a session that cannot read
  or verify the set does not start (`GUARDRAILS_UNAVAILABLE`). File tools are
  refused under `$SLAUDE_HOME/guardrails` and on the database file.
- **`/deploy` payload version 5** carries the deploy repo's guardrails as a
  top-level list. A gateway older than rc.9 refuses such a payload instead of
  dropping the guardrails. A console override (phase B) is kept across syncs
  and flagged *behind source*.
- **Nodes.** The guardrails ride in the runtime bundle with their version in
  the ETag; a change reloads nodes and warm sessions. Nodes advertise a
  `guardrails/1` capability: an agent with enforced rules is never run by a
  node without it (its bundle is refused, and the dispatcher waits for a
  capable node, then tells the thread).
- **Console.** Resources > Guardrails is now the owner's list and a page per
  guardrail (`GUARDRAIL.md` rendered, raw and copy; the rules with *Enforced*
  labels; Guidance; problems; who it applies to; recent firings; the source
  and the behind-source flag; how strongly this deployment keeps an agent from
  changing its guardrails). Each agent page gains a Guardrails tab. A
  superadmin can switch a guardrail off and on (audited); operators read. The
  rc.7 runtime-layer sections and their API fields (`promptStack`,
  `baseline`, `builtinSkills`, `guardrails`) are removed; the registry stays
  in the code as a drift check. The soul and access cards move under a
  collapsed *Soul and access settings* section (their API is now
  `GET /panel/api/guardrails/settings?agent=`).
- **Fail closed where it matters.** Padding cannot hide a value: strings are
  matched whole up to 1 MB, and an input or message too large to check is
  refused by deny and approve rules. A write checks the stored set first, so
  it can never re-sign tampering; the owner repairs a broken set with
  `slaude guardrails import --repair`. A high-water mark (in the process, a
  file beside the key, and Redis on cluster deployments) makes a deleted or
  rolled-back set fail closed. While the set fails to verify, inbound messages
  are dropped with a notice. A rule that fails to parse refuses the `/deploy`
  (422), the import and `personas render`.
- **Audit.** `guardrail.tool.denied|audited`, `guardrail.inbound.denied|audited`,
  `guardrail.guidance.delivered`, `guardrail.created|updated|deleted|repaired`,
  `guardrail.node.unsupported` and `guardrail.integrity.failed`. Rows name the
  agent, channel, tool and rule, never the tool input or the message text.

**Upgrade notes.** Migration `0033` is additive. A deployment with no
guardrails behaves as before (no bundle field, the same ETags, and the signing
key is never read or created). On sqlite without `SLAUDE_MASTER_KEY` the key is
created on the first guardrail write under `$SLAUDE_HOME/guardrails/.hmac-key`;
on Postgres guardrails require `SLAUDE_MASTER_KEY`.

**Console API change.** `GET /panel/api/guardrails` changed shape: it no
longer takes `?agent=` and returns the owner guardrail list
(`OwnerGuardrailsResponse`). The soul and access settings it used to return are
at `GET /panel/api/guardrails/settings?agent=` (`{ agent, families }`), without
the rc.7 fields `promptStack`, `baseline`, `builtinSkills` and `guardrails`. Upgrade nodes before adding a
guardrail with enforced rules: until a node runs rc.9 it is refused that
agent's turns.

#### rc.7

**Guardrails as the runtime layer.** The Guardrails page (rc.4) showed mostly
soul and access settings, which belong to an agent and to Access. What an
operator means by guardrails is the runtime's own layer, the part a soul cannot
turn off: the fixed baseline of the system prompt under every persona, and the
hooks and gates that block, rewrite or stop the agent. Most of it was
invisible, and the page was a hand-kept description that could drift from what
runs. See the
[guardrails runtime layer field note](../field-notes/2026-11-08-guardrails-runtime-layer.md).

- **System prompt.** The page now opens with the layers every session gets, in
  order (the Claude Code preset, the runtime baseline, the persona, channel
  mandates, the session mode, the MCP list, memory context), each marked *Fixed
  by the runtime* or *From the soul*, with the persona and channel mandate
  linking to the agent's Mandates tab. Each block of the runtime baseline opens
  as rendered markdown with Raw and Copy; the baseline is one render for every
  agent of the deployment, and the page says so. Built-in skills are listed
  with the tools they gate. The page also says plainly that nothing in the
  code stops a soul from contradicting the baseline.
- **Hooks and gates.** Every SDK hook and gate the runtime wires, with its
  event, what it does, where it applies (threads, wakes, remote, voice,
  background), how it is switched, and a state: *Enforcing*, *Shadow* (the
  decision gate in shadow mode), *Off*, *Not wired* or *Not built*. *Not
  wired* means the code exists but this deployment does not install it: in the
  gateway role the must-reply Stop guard showed *Not wired* in rc.7, because
  the node worker installed none (fixed in rc.8). The KB-first Stop guard and policy guardrails Tier 2
  and 3 show *Not built*, linking their designs. Hooks that only count or
  report sit behind the Kind filter.
- **Limits and deny lists.** The CLI scheduler tools, the wake allow-list, the
  remote deny list, the background pass lockdown, the child environment scrub,
  built-in skill write refusal, `soul_override` for the manager only, the
  outbound fetch policy, budgets and wake caps, secret masking and the soul's
  redaction patterns (values for superadmins, a count for operators).
- **Two behaviour gaps found, not fixed in rc.7** (follow-ups; this candidate
  only describes what runs; both fixed in rc.8, see Fixes):
  - A node worker installs no Stop guard, so the must-reply rule is not
    enforced for turns that run on nodes: a node turn that ends without a reply
    or a `pass` is not sent back.
  - A wake that runs on a node can use tools the node's own permission policy
    auto-allows (its `SLAUDE_AUTO_ALLOW_TOOLS`). The node answers those calls
    locally, so they never reach the gateway, where the wake refusal lives; in
    mono every permission request during a wake is refused. The page notes
    this on the wake refusal row in the gateway role.
- **API.** `GET /panel/api/guardrails?agent=` adds `promptStack`, `baseline`,
  `builtinSkills` and `guardrails` beside the existing `families`, which stay
  (the soul and access cards move to the agent's tabs in a later candidate).
  Environment values appear only as on or off, a mode or a cap.

### Fixes

**Console sessions (rc.2), found in a live smoke test of rc.1:**

- **A reply sent through the reply tool was invisible in the console.** While an
  operator held a session, the reply was kept out of Slack (correct) but the
  console only rendered streamed text, so the answer was lost. Replies now show
  as the agent's messages with a marker: sent to Slack, held in console, or not
  sent.
- **A session had no history.** Timeline and Chat started empty. They now show
  earlier turns from the agent's own conversation record
  (`GET /panel/api/sessions/:id/history`, the agent's slice only, redacted).
- **What people said in Slack was missing from the live view.** Delivered Slack
  messages now appear on the session stream (display only; never fed to the
  model). In mono the live view received no events at all; it does now.
- **Tool calls never paired with their results.** Tool events now carry the
  tool use id and the result names its tool.
- **"Running" meant a warm process, not a turn in flight**, and rows stayed
  running for days after a node restart. The console now shows Working, Warm
  or Idle from the warm registry and the event stream, and the overview card
  counts active (warm) sessions. The sessions list reads liveness in a few
  batched round trips.
- **The context meter passed 100%.** It summed every model call in a turn; it
  now uses the last call's prompt and the display caps at 100% with the token
  count.
- **Behaviour change (agent loop):** a turn answered only through the reply tool
  is now written to the conversation record, but only once the reply is
  delivered (a reply held in the console counts). Before, such turns were not
  recorded, so `<recent-turns>` missed them.

**Console polish (rc.3), found in a live smoke test of the new console:**

- **Mandates of a filesystem persona were missing.** With no structured
  `soul_json`, the Mandates tab listed only channel blocks inherited from the
  default soul. Mandates now come from the persona's own soul text, with the
  same fallback the scheduler uses (the extraction cache, else the
  `## Mandate` / `### Mandate` parse). The Heartbeat mandate shows whenever
  wakes are on anywhere, including a channel's own `### Proactive` with
  `Enabled: yes`. Titles show `#channel-name`, never `<#C123>`.
- **Channel ids instead of names.** The gateway now resolves channel names
  (and `DM with <name>`) through a cached `conversations.info` / `users.info`
  lookup with the right app's client, and the API carries them for sessions,
  the session header, mandates and audit rows. A failed lookup shows the id.
- **The sessions list loaded everything and showed no model.** It pages 50 at
  a time with Load more. The Model column shows the session's model, else the
  agent's configured model, else "Deployment default".
- **Raw Slack markup in messages.** Links, `@name` mentions, `#channel`
  references and `&amp;`-style escapes are rendered the way Slack shows them,
  in the console only (stored text is unchanged).
- **Audit rows said "Operator" for a superadmin, and console sign-ins belonged
  to the default agent.** The actor column now shows the recorded console
  role. Sign-in, console roles and config reload are recorded with no agent
  and shown as Console, older sign-in rows included.
- **Memory page titles were slugs.** Pages show their frontmatter or own
  title; a session's conversation record reads "Conversation <date> (<short
  id>)", with the slug as secondary text.
- **My agents told an unlinked account to ask a manager.** With no Slack
  identity linked it now says so and how to link one (send `/link` to the agent).
- **History times were misleading.** A turn's user line and reply shared the
  record's write time. The user line now carries its Slack message time; a
  line with only a day recorded shows the date, not a clock time.

- **A wake could not save to memory.** Its initiator is the agent's own id,
  and the memory gate read that as a person in a public channel, so every
  write was refused and the agent noted it had no write tool. The gate now
  treats the agent's own id as no person, like any background turn.
- **A soul edit dropped a named persona to the summarising round and blanked
  its mandate.** Its manager and mandates came only from the LLM extraction
  cache, which is empty for new soul text. The scheduler now parses the
  manager (`## Reporting`) and mandates (`## Mandate`, per channel
  `### Mandate`) from the soul text when the cache has no entry.
- **A message sent during a running skill check hung its thread.** The CLI
  folds input sent during a running turn into that turn, so one result
  answered both and was taken as the check's. The node's turn never ended and
  the thread sat until the 15 minute turn timeout. A message now waits for
  the check to finish.
- **A node tool call waiting on an approval card posted a new card every
  five minutes.** The call held one HTTP request; Bun's `fetch` cut it at
  300 s and `postTool` resent it, so each resend posted another card, the
  model never got the auto-deny and the turn died at its timeout. `postTool`
  now sends once, with no fetch limit, and carries the turn's abort signal.
- **`proactive_rule` was used for format wishes.** A live agent recorded "include
  links" as an `act` rule. The tool description and the runtime prompt now
  keep a rule for how far the agent may go with a kind of item; what a post
  should contain goes to `self/heartbeat` or memory.
- **Any viewer could approve a tool permission card.** The click handler
  resolved the gate for whoever clicked. A click is now authorised before any
  resolve, and a refusal is audited as `gate.permission.refused`.
- **A bystander could become the requester.** The requester was read from the
  session's route context, which every delivered message rewrites, so someone
  posting during a cron, console or another person's turn could approve its
  cards. The requester is now the single Slack sender of the turn's inputs;
  on nodes, the job's initiator only when it is the job's single recorded
  sender.
- **Named personas used the default persona's access rules** for admission,
  `/1on1`, admin commands and approvals. They now use their own.
- **A deny grant did not reach the default persona's approval cards.** The
  default persona's approvers came from SOUL.md, the legacy list and the env
  list without consulting grants, so a denied user named there could still
  approve, and anyone could click a card with no approvers. Denied users are
  now dropped from the list and refused at click time on every persona.
- **Operators could read the console allowlist.** The console roles endpoint
  listed every console user's email to any operator; it is superadmin only now.
- **A channel grant accepted a DM id.** `D` ids are refused with a pointer to
  DM-only user grants, in the API and in the console form.

#### rc.5

**Brain embedding model**, see the
[embedding provider field note](../field-notes/2026-11-08-embedding-provider.md):

- **Chunks were labelled with gbrain's default model, whatever embedded them.**
  gbrain's chunk write stores `chunk.model || DEFAULT_EMBEDDING_MODEL`
  (`zeroentropyai:zembed-1`), and none of its writers (`put_page`, KB sync, the
  embed sweep) set `chunk.model`. A brain configured for another provider got
  its vectors from that provider but carried the default label on every chunk
  written since. slaude now labels every chunk write so the label describes
  the vector: the configured model where the process embeds, the brain's own
  record elsewhere. Only a bundle import keeps the labels it carries.
- **No guard against a second model in one vector column.** At boot slaude now
  compares the process's `EMBEDDING_PROVIDER` / `EMBEDDING_MODEL` /
  `EMBEDDING_DIMENSIONS` with the brain's record (gbrain's `config` table). A
  provider-prefix-only difference (`openai:x` vs `litellm:x`) is adopted. A
  different model name is probed: up to 6 stored chunks, one per page, spread
  across sources and both ends of the update history, are re-embedded and
  compared with their stored vectors. Only when every sample matches (cosine
  0.99 or above) is the configured name adopted; one miss, or chunk labels
  that already name two models, logs `EMBEDDING REFUSED` and turns embedding
  off in that process (writes land unembedded instead of mixing models). The
  probe runs in the background: the boot never waits for the embedding
  provider, and a close never waits for the probe's provider call. A probe
  that fails or times out keeps embedding on with a warning. Other dimensions
  refuse. A vector the gateway produced with another model is dropped at write
  time, with the same loud log.
- **Upgrading a brain created between mid-June and early October 2026.** Those
  brains' record names gbrain's seeded default while every vector came from the
  configured model. The first boot of rc.5 probes and adopts the configured
  name, logging `[brain] embedding record adopted: <old> -> <new> (probe ok)`
  once. If the provider is unreachable at that boot, embedding stays on and the
  next boot probes again; `slaude brain reembed --adopt --apply` records it by
  hand.
- **Repair: `slaude brain reembed`.** `--model-mismatch` lists pages with
  chunks labelled with another model (dry run by default) and, with `--apply`,
  re-embeds them with the configured model through gbrain's own APIs. It
  re-reads each page inside the write transaction and skips pages changed
  meanwhile (safe beside a running gateway on Postgres), keeps modality and
  token counts, covers soft-deleted pages, and resumes a whole-brain run.
  `--adopt` records the configured model without touching a vector. Run either
  where the brain engine runs with the deployment's embedding env (the gateway
  container, or the brain server in remote mode).

#### rc.6

**Console and portal, found in a live smoke of rc.5** (no schema change):

- **An agent actor read as its bot user id.** An event the agent did itself
  (actor kind `agent`, such as the weekly skill review retiring a skill)
  records the agent's bot user id, so Overview's Recent activity and the audit
  list showed an opaque `U...` id labelled Agent. The audit answers now carry
  `actorLabel`, the name of the agent whose bot id it is (else the row's
  persona), and the audit table, event drawer and session timeline show that
  name, with the id as secondary text.
- **The portal assumed Slack.** Slack is one chat surface of several to come
  (WhatsApp, Discord, Telegram). My account said *Linked Slack identities*
  with a *Slack user* column, and My agents and the `/portal/link` page spoke
  of Slack users. Identities and agents now carry a `surface` (`slack` today);
  the pages say *Linked chat identities* and show a Surface column labelled
  from the console's surface registry, then Workspace and User by name with
  the id as secondary text. The link page gains a Surface row filled from a
  data attribute by its existing nonce script, so its strict CSP is unchanged.
- **Workspace and user names did not resolve in the portal.** The portal asks
  for names with only a team id. With one Slack app per persona in one
  workspace that id matches several apps, so no lookup client was chosen (and
  the default agent may have no thread to name its app), and the pages showed
  raw ids. Such a lookup now uses any registered app of that workspace, picked
  by app id so the choice is stable. It still goes through the console's
  lookup clients (no retries, rate limits rejected, 2 s deadline).
- **A deployment kept teaching the old memory tool names.** The bundled
  `how-slaude-works` skill already teaches `memory_search`, `memory_think` and
  `memory_save`, but bundled skills were only seeded when missing, so a
  deployment seeded before the rename kept a copy that taught `kb_search`,
  `kb_think` and `kb_memoize` (still working aliases). The seeder now records
  the hash of what it wrote (`skills/.bundled.json`) and refreshes only a copy
  that is exactly a release's: the recorded hash, or, for a copy seeded before
  that record existed, one of the previously shipped versions listed by hash.
  Any other copy (an operator edit, `write_skill`) is customised and left
  alone, logged once per boot, with a note when it still names the `kb_*`
  tools. The seeder never writes through a symlinked skill directory or
  SKILL.md, and it writes SKILL.md and the record through a temp file and a
  rename, so seeders sharing `SLAUDE_HOME` cannot leave a half-written file.
  No other built-in skill or runtime prompt named the old tools.
- **The copy button gave no feedback.** The Copy button on markdown views
  (*Copy SKILL.md* and the like) and code blocks copied, but only swapped its
  icon briefly, and a refused clipboard was silent. It now shows *Copied* (or
  *Copy failed*) beside the icon for about two seconds, renames itself to
  match, and announces the result through a polite live region.

**Node guards (rc.8), the two gaps the rc.7 guardrails survey found** (no
schema change; see the
[guardrails field note](../field-notes/2026-11-08-guardrails-runtime-layer.md)):

- **On cluster deployments a turn that ends silently is now sent back once.**
  The must-reply rule (a turn ends with a reply, an edit, an upload or a
  `pass`) was enforced only in mono: the gateway installs the Stop guard on
  its own AgentManager, but in the gateway role turns run on node workers,
  which installed none, so a node turn that ended with nothing user-visible
  just ended and the person who asked saw no answer. Each node worker now
  installs the same guard: it tracks reply, edit, upload and `pass` from the
  node's own tool calls, resets them per job, and blocks the first silent stop
  with the same instruction as mono (a second stop is let through and
  counted, as before). The tool list and the instruction are one shared
  module used by both, so the two cannot drift. It forces only what mono
  forces: a turn a person started (origin `slack` or `panel` in the signed job
  token). Cron runs, promise checks, heartbeat turns, wakes and voice turns
  are never sent back, as in mono, where all of those run on silent routes.
  The console's Guardrails page now shows the must-reply row as *Enforcing* in
  the gateway role.
- **A message no longer joins a queued turn of another kind.** In the gateway
  role a message that arrives while the thread's previous turn is still
  queued is merged into it, and the merged turn runs under the first job's
  token. A person's reply behind a queued heartbeat wake therefore ran as the
  wake (never sent back, and with this release every tool refused), and a
  promise check merged into a waiting Slack turn lost its ledger run and could
  be sent back. Jobs now merge only when their origin, background run and
  wake agree; otherwise the message is queued as its own turn and runs right
  after, in order.
- **Mono applies the guard per turn the same way.** A person's message in a
  thread whose last turn was a cron run reused that run's silent route, so the
  must-reply guard stayed off for it; it is now guarded. A console (panel)
  message reused the route without resetting it, so a reply from the previous
  turn satisfied the guard; each console turn now starts over, as on nodes.
- **Wake turns on nodes refuse every tool, like mono.** Nobody is in a wake's
  turn to click a permission card, so mono refuses every permission request
  during a wake before any policy runs. A node answered from its own policy
  first, so a tool in the node's `SLAUDE_AUTO_ALLOW_TOOLS` (a built-in such as
  `Bash`, if listed there) ran during a wake without ever reaching the
  gateway's refusal. The node resolver now refuses with the same wake refusal
  first, when the job's signed `wake` claim or its own `wake` field says it is
  a wake. The next normal turn on the same session binds its own token, so
  ordinary threads keep the node's auto-allow list unchanged. A voice call on a
  session whose last job was a wake is refused the same way until the next
  normal turn (see the field note).
