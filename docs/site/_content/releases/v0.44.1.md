## v0.44.1 — Slack HTTP-mode fixes, approval cards that survive, and the gateway/node Secret split (draft)

> [!NOTE]
> **Draft, not released.** These notes describe the patch-class work of the HA
> series: bug fixes, a warning and a manifest change, with no schema change, no
> install-path change and no agent-loop change. All of it was developed on one
> integration branch together with the v0.45.0 work, and `main` already carries
> feature work since v0.44.0 (personas as code, the portal, `/remote`,
> gateway-owned MCP credentials). A v0.44.1 that is truly patch-class must be cut
> from `v0.44.0` with these fixes picked onto it; otherwise these items ship in
> v0.45.0 and this file is folded into its notes. The maintainer decides at the
> release.

### Fixes

- **HTTP mode no longer reads `SLACK_BOT_TOKEN` per message.** Apps come from
  the encrypted `slack_apps` registry in HTTP mode, but the attachment path still
  read the bot token from the environment and dropped the turn when it was unset.
  The token now comes from the event's own app, and only when the message has
  files.
- **Every Slack method reaches the app.** The lazy client forwarded a
  hand-written list of methods, which had already missed `chat.postEphemeral`
  (the portal link was never delivered) and still missed `files.uploadV2`
  (attachment replies), `chat.delete`, pins, topic and purpose, and canvases. It
  now forwards any method.
- **`users.profile:write` is a user scope.** The manifest emitted it as a bot
  scope, which Slack rejects; install now passes it as `user_scope`.
- **No raw error text in Slack.** A failed turn posts a fixed message for its
  typed failure code, once per job; the raw error goes to the log, redacted.
- **A second approval click no longer erases the decision.** The second click
  replaced the decided card with "already decided", and the card is the only
  visible record. It now answers ephemerally and leaves the card alone. An
  expired or cancelled gate says so.
- **`/mcp` in Slack and the portal agree**: Connect cards and `/mcp connect`
  resolve servers per persona, from the same list the portal shows. A card for a
  server the persona no longer mounts is reported instead of silently approved.
- **The portal has an Unlink button** per Slack identity.
- **The gateway's own model children have no shell.** The `kb_think` synthesis
  child was started with an empty `allowedTools`, which the SDK drops, so the CLI
  ran with every tool and `bypassPermissions`; a prompt-injected knowledge page
  could run Bash. It now runs with no tools and `dontAsk`, and page content can no
  longer be read as a slash command.

### Features

- **Versioned `/deploy` payload.** The persona sync payload carries `version`.
  A field the gateway does not know is logged by name and returned as
  `ignoredFields` (a 422 with `SLAUDE_DEPLOY_STRICT=1`); a newer `version` than
  the gateway supports is refused. Before this, an older gateway silently dropped
  a newer field. See [Personas as code](../deploy/personas-as-code.md).
- **The gateway/node Secret split, stage one.** `deploy/k8s-scale` now has two
  Secrets: the gateway's (master key, job secret, database URLs, Slack secrets,
  deploy tokens) and the node's (its credential, Redis, the provider fallback).
  The gateway runs under its own ServiceAccount; node pods mount no
  ServiceAccount token. A node that finds a gateway-only variable in its
  environment **warns** at boot and sets `slaude_node_gateway_secrets_present`;
  `SLAUDE_NODE_BOOT_CHECK=refuse` makes it refuse. The agent child is scrubbed of
  every gateway-only variable, and `.mcp.json` placeholders never expand one. An
  optional NetworkPolicy keeps nodes off the Postgres and Vault ports. See
  [the Secret split](../deploy/multi-node.md#the-secret-split).

> [!WARNING]
> **After the split, treat `SLAUDE_JOB_SECRET` and `SLAUDE_MASTER_KEY` as exposed**
> on any cluster that ran nodes with the shared Secret. `SLAUDE_JOB_SECRET` can be
> rotated now (drain, change, restart gateways). `SLAUDE_MASTER_KEY` cannot be
> rotated safely yet: there is no re-encryption tool, and a managed gateway with a
> new key can fail to start. See
> [What nodes were exposed to](../deploy/multi-node.md#what-nodes-were-exposed-to).

**Upgrade order:** gateways first, then nodes. Apply the node manifest only with
the node image already at this release, and let queued turns drain first.

### Internal

- **Local cluster harness.** `up.sh` waits for Postgres over TCP (the image's
  socket-only init server had raced database creation); the verify scripts report
  COULD NOT MEASURE with a reason instead of a wrong number, log every diagnostic
  to a named file, and pin the node autoscaler for the run; `forward.sh` is a
  self-healing port-forward; sizing lives in one file with a test; the cluster
  model can be set with `SLAUDE_LOCAL_MODEL`.
